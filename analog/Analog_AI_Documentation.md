# Analog Design — AI Usage Documentation

A running record of every use of AI assistance in the analog design work for
the ENGN 2912E SNN project: what was asked, what the AI did, what it produced,
and how far its output was checked. It is updated as the work continues.

- **Tool:** Claude Code (desktop app), model Claude Opus 5.5 (Anthropic)
- **User:** Ray Wu
- **Started:** 2026-10-25
- **Last updated:** 2026-11-11

---

## How AI is used in this project

| Category | What the AI does | What the AI does *not* do |
|---|---|---|
| Schematic / testbench review | Reads `.sch` files as text, works out connectivity from pin coordinates, points out wiring, topology and SPICE-setup errors | Edit existing schematics: changes to the user's schematics are made by the user in xschem. *Exception (2026-11-03, user approved):* the AI created the new `neuron_5khz*` files (entry 28). |
| Simulation debugging | Explains ngspice/xschem error messages and proposes fixes | Run xschem or ngspice without asking. *Exception (2026-11-03, user approved):* the AI ran xschem netlisting and ngspice in the user's iic-osic-tools container, with scratch output in the container's `/tmp` only (entry 28). |
| Results analysis | Reads `wrdata` text output (`*_tb.txt`) with short Python scripts and reports measured values (thresholds, step sizes, reset levels, timing) | Generate simulation data (except entry 28, as above) |
| Circuit explanation | Explains circuit operation (e.g. Indiveri et al. 2011, Figure 4) and design trade-offs | Choose final device sizes or architecture. *Exception:* entry 28, where the user asked the AI to size a copy of the neuron. |
| Estimates | Rough area and sizing estimates from rules of thumb | Provide sign-off numbers: no layout exists yet |
| Documentation | Writes and maintains Markdown logs | |

**Verification levels used below:**
- **Simulated:** numbers from ngspice runs the AI made itself (only entry 28, with the user's approval).
- **Analysed:** numbers computed by the AI from the user's own simulation output files.
- **Reasoned:** derived from reading files or from circuit theory; not simulated.
- **Estimate:** rule-of-thumb figure that needs checking against the PDK or a layout.

### 2026-10-25

**1. Review of the Schmitt-trigger comparator testbench** *(Reasoned)*
- **Asked:** review `schmitt_trigger_comparator_testbench.sch` without editing files.
- **AI found:**

**2. "Undriven node" netlist errors** *(Reasoned)*
- **Asked:** debug undriven-node errors from netlisting.
- **AI did:** without seeing the error text, listed likely causes; the main one was floating transistor body pins. Asked for the exact messages.
- **Outcome:** the user wired the body pins.

**3. Triangle-wave transient on the comparator** *(Reasoned)*
- **Asked:** why the transient triangle input wasn't working.
- **AI found:** `.param` inside `.control` (parameters undefined); a one-direction current pulse into a cap can't make a triangle; the run was ~100× shorter than the waveform period.
- **AI suggested:** drive the input with a voltage `pwl` triangle and move `.param` outside `.control`.

**4. Input source for an SNN neuron** *(Reasoned)*
- **Asked:** what input current source suits a comparator inside an SNN.
- **AI explained:** switched (pulsed) unipolar current into a membrane capacitor with a reset, based on the behavioural models in `analog/mock/` (`dac.v`, `neuron.v`, `comparator.v`).

### 2026-10-26

**5. "unknown subckt … neuron" in `neuron_testbench`** *(Reasoned)*
- **AI found:** the `plot` title opened with `'` and closed with `"`, which ended the code block's `value="…"` early. The `.control` block lost its `.endc` and swallowed the `.subckt` definition. Also: `v(spike)` named a node that doesn't exist.

**6. "tran simulation(s) aborted"** *(Reasoned)*
- **AI explained:** the vector errors were a result of the sim failing at the DC operating point (MEM nearly floating; feedback loop). Suggested `.ic v(mem)=0` with `tran … uic`, or a leak resistor, plus a maximum time step.

**7. Singular matrix at `vbias#branch`** *(Reasoned)*
- **AI found:** the label on Vbias's + terminal said `VDD`, putting the 0.2 V source in parallel with the 3.3 V supply and leaving `reset_bias` floating.
- **Outcome:** the user relabelled it `reset_bias`.

**8. Plotting the input current** *(Reasoned)*
- **AI explained:** use the series ammeter's branch current (`i(vmem)`). Flagged that the ammeter's instance name must start with `V`: `iMEM` would netlist as a 0 A current source.
- **Outcome:** the user renamed it `VMEM`.

**9. Access to simulation results** *(Reasoned)*
- **AI explained:** it couldn't see results, because ngspice wrote them inside the container. Suggested `write`/`wrdata` with absolute `/foss/designs/...` paths.
- **Outcome:** the user added the paths; later results were readable.

**10. Staircase on MEM, no reset (ipk = 1 nA)** *(Analysed)*
- **AI measured:** MEM rose ≈ 51 mV per input pulse, reaching only ≈ 0.53 V in 10 ms; VOUT stayed at 3.3 V.
- **AI explained:** the staircase is expected for pulsed input; the neuron never reached its threshold. Also flagged a `v(out)` typo in `wrdata`.

**11. Reset not fast enough (ipk = 1 µA)** *(Analysed)*
- **AI measured:** about 67 spikes per input pulse; reset fall ≈ 9 ns, but MEM only dropped from ≈ 1.96 V to ≈ 1.21 V.
- **AI explained:** the reset ends itself when MEM drops below the lower threshold. Suggested holding the reset for a fixed time (one-shot or latch), widening M1, lowering the input current, and using finer time steps.
- **Outcome:** the user widened M1 to W = 2 µm and added C2 = 100 fF on the reset gate.

**12. MEM not crossing threshold (back at ipk = 1 nA)** *(Analysed)*
- **AI explained:** VP is an internal node, not the firing threshold. MEM needed ≈ 38 pulses to reach VTH+. Gave a table of ipk versus pulses-to-fire and suggested 10 nA.

**13. Measuring VTH+ / VTH−** *(Reasoned)*
- **AI suggested:** a slow `pwl` triangle on the comparator alone, with `meas tran … WHEN v(vout)=1.65 FALL=1 / RISE=1` and `plot v(vout) vs v(in)`. Explained the `pwl` syntax on request.

**14. Simulation log created** *(Analysed)*

**30. Description of `_user_prompt` in `advisor.py`** *(Reasoned)*
- **Asked:** add a description of the user prompt to this file.
- **What it is:** each request to the model carries two messages. The *system prompt* (`SYSTEM_PROMPT`) is the fixed job description, the same every call. The *user prompt* is the specific question for this round, rebuilt each call by `_user_prompt(space, history, spec, n)` so it always includes the latest simulation results.
- **Inputs:** `space` (the tunable parameters and their bounds), `history` (every point simulated so far, with its measured metrics), `spec` (acceptable range per metric), and `n` (how many new candidates to ask for).
- **How it works:** it collects lines of text in a list, then joins them with line breaks into one block of text. It has four parts:
  1. **Parameters:** one line per knob with its minimum, maximum and grid step.
  2. **Spec:** one line per metric with its acceptable range.
  3. **Simulated points:** a comma-separated table with a header row (parameter names, metric names, `meets_spec`), then one row per simulated point with its values and pass/fail. If nothing has been simulated, it says so.
  4. **Request:** "Propose exactly n new candidates."
- **Example output** (two parameters, one metric, one simulated point):
  ```
  Parameters (name: lo .. hi, step):
    WP: 2.2e-07 .. 2e-06, step 5e-09
    WN: 2.2e-07 .. 2e-06, step 5e-09

  Spec (metric: acceptable range):
    vth_hi: 1.95 .. 2.05

  Simulated points:
    WP,WN,vth_hi,meets_spec
    4.4e-07,2.2e-07,1.5,False

  Propose exactly 4 new candidates.
  ```
- **Why a plain-text table:** it is compact, so many points fit in one request, and models read comma-separated tables reliably. `:.4g` rounds each number to 4 significant figures to keep it short.

**36. Checking the user's peak-current equation, C·ΔV + I_lk·ΔT** *(Reasoned)*
- **Asked:** the user derived I_peak = C·ΔV + I_lk·ΔT, which differs from entry 33.
- **AI explained:**
  - That expression is a *charge* (coulombs), not a current. It is the correct charge balance, the same as entry 33's Q plus leak charge.
  - To get a current, divide by the total pulse on-time: I_pk = (C·ΔV + I_lk·ΔT) / (N·t_on), with t_on = pw + (tr + tf)/2.

**40. Refractory period versus reset** *(Reasoned)*
- **Asked:** what the refractory period is, and whether it's just the reset.
- **AI explained:**
  - Reset (down-swing) is the fast discharge of VMEM to ground once I_K turns on. It lasts roughly C_mem·ΔV/(I_K − I_in), well under a µs to a few µs.

  - In this schematic the refractory period overlaps most of the spike's falling edge, because both come from the same C_K discharge.

**49. How the 3-5-1 SNN computes (ML principles)** *(Reasoned / Estimate)*
- **Asked:** explain the machine-learning principles behind the 3-5-1 SNN; the user knows the circuits but not how a computation is done.
- **AI explained:**
  - Rate coding: each neuron computes output rate = f(Σ weight × input rate − leak), the same form as an artificial neuron y = f(Σ w·x + b). Spike × DAC current is the multiply, KCL at VMEM the sum, the leak (Vlk) the bias, and integrate-and-fire the activation function.

  - Weights are found offline (by hand or by training a software rate model with non-negative, quantized weights) and loaded into `rf`; there is no on-chip learning.

**53. Can the SNN solve XOR?** *(Reasoned)*

**62. Trade-offs of MOS decoupling caps on the bias lines** *(Reasoned / Estimate)*
- **Asked:** the trade-offs of adding MOS capacitors to decouple the bias lines (versus re-routing net1, entry 61).
- **AI explained:**
  - **Peak vs. charge:** a decap lowers the glitch peak (ΔV = Cc·Vstep / Ctot), but with a resistive bias source the integral ∫ΔV dt = Cc·Vstep·Rsrc does not depend on the decap. It helps (a) when the aggressor pulse is shorter than τ = Rsrc·Ctot, so the rising and falling edges cancel, and (b) by cutting the exponential rectification of large glitches in subthreshold devices. Re-routing lowers Cc itself, which helps in every case.
  - **Settling:** *(Estimate)* a subthreshold diode-connected bias source has Rsrc ≈ n·UT/I ≈ 35 MΩ at 1 nA. With 100 fF, τ ≈ 3.5 µs; at 10 pA it is about 0.35 ms. This slows bias start-up and reprogramming.
  - **Cap type and voltage:** an NMOS inversion cap at a subthreshold gate voltage (below Vth) is in depletion and gives only a fraction of Cox. An accumulation varactor (PDK `cap_nmos_b`/`cap_pmos_b`, to be checked in the PDK docs) or a MIM cap avoids this. MIM is linear but about 2 fF/µm² and needs M4/M5, already used by C1/C2.
  - **Reference rail:** reference the decap to the rail the bias is relative to (NMOS biases to VSS, PMOS biases to VDD). Otherwise supply noise couples into Vgs.
  - **Area:** *(Estimate)* about 5 fF/µm² gate cap; 100 fF per line ≈ 20 µm²; 8 lines ≈ 160 µm² per neuron, × 9 neurons. FEOL area under the MIM caps (the routing channel) could hold some of it.
  - **Leakage:** 3.3 V gate oxide leakage is negligible.
  - **Top level:** bias lines are shared by all neurons and run across the chip, which is likely the larger exposure. Decoupling at the bias generator (or per row) covers that once.
- **Recommendation:** re-route net1 below the bias tracks (no area, lowers Cc); add decoupling at the bias generators, sized so τ is much longer than the aggressor pulse width and much shorter than the bias reprogramming time; per-neuron decaps only if simulation shows a need.
- **Not done by AI:** no files changed other than this log; nothing simulated.
